# OpenEMR Agent

A fork of [OpenEMR](https://github.com/openemr/openemr) used to build and demo a clinical AI agent. This section covers what's specific to the fork: how to run it on Windows, what sample data is loaded, and how to check that everything works. The original OpenEMR README is [further down](#openemr).

- **Repo:** `https://labs.gauntletai.com/debudash/openemragent`
- **Based on:** OpenEMR master (`7b887fb`, a trimmed copy)
- **All patient data is synthetic** (generated by [Synthea](https://github.com/synthetichealth/synthea)). Don't point this stack or its tests at a system with real patients.

## Live demo

A public deployment on Railway, so you can look around without installing anything:

**https://openemr-production-461d.up.railway.app**

| Sign in as | What it's for |
|---|---|
| `admin` | Full administrator. User administration, globals, all 50 patients. |
| `doctor1` | Dr. Dana Reyes, MD — provider (Physicians group) with **25 patients** assigned. |
| `doctor2` | Dr. Samir Okafor, MD — provider (Physicians group) with the **other 25 patients**. |

**Passwords are not in this repository.** Email Debu Dash (the repo owner) to request them.
Ask for the agent's shared secret at the same time if you want to run the
[API collection](api/) against the live service — it is the credential every call to the agent
is signed with, so it is kept out of the repository for the same reason the passwords are.

**What's loaded:** 50 Synthea patients, ~2,800 encounters, ~1,400 problems, ~300 prescriptions, ~9,900 lab results and ~700 immunizations. Every patient has one assigned provider, split evenly between the two doctors.

**Expect `doctor1` to see all 50 patients**, not just their 25. OpenEMR's permissions are role-based, so an assigned provider is a data attribute, not an access restriction — see [AUDIT.md](AUDIT.md) S3. Restricting a clinician to their own panel is the agent's job, specified as REQ-SCOPE-1 in [USER.md](USER.md).

**A quick look around:** sign in, then **Patient → Patients** to search (names carry Synthea's numeric suffixes, e.g. `Blair400 Wiegand701`). Open a chart for problems, medications, labs and encounters. As `admin`, **Admin → Users** shows the two provider accounts.

**The API is open too** (OAuth2 + FHIR R4, US Core 3.1.0):

```bash
curl https://openemr-production-461d.up.railway.app/apis/default/fhir/metadata          # capability statement, no auth
curl https://openemr-production-461d.up.railway.app/apis/default/fhir/Patient           # 401 without a token, as expected
```

To pull actual records you need a token; [usecases/USECASES.md](usecases/USECASES.md) shows the full OAuth flow, and the test suite runs against this deployment.

> **Synthetic data only.** The deployment exists to be inspected and holds nothing but generated records. Never put real patient data on it. Credentials are shared on request rather than committed, so they can be rotated without touching git history. Setup and cost details are in [deploy/railway/README.md](deploy/railway/README.md).

## Clinical Co-Pilot (the agent)

The **CopilotAgent** tab in the top menu opens a two-pane page: the signed-in physician's rounding list for today on the left, the selected patient's pre-rounding brief and a follow-up conversation on the right. Every statement is cited to a chart record and verified before it is shown; every response carries one of four states (complete for requested scope, partial, unable to answer, access denied).

- Built to [requirements/AgentForge_Clinical_Copilot_PRD.pdf](requirements/AgentForge_Clinical_Copilot_PRD.pdf), within [USER.md](USER.md) §4 boundaries and [AUDIT.md](AUDIT.md) findings.
- Agent code, evals and grounding rules: [copilot/](copilot/) ([README](copilot/README.md), [GROUNDING_RULES.md](copilot/evals/stage1/GROUNDING_RULES.md)).
- OpenEMR module (gateway, scope, UI): [interface/modules/custom_modules/oe-module-copilot-agent/](interface/modules/custom_modules/oe-module-copilot-agent/).
- Design and evidence: [ARCHITECTURE.md](ARCHITECTURE.md), [SECURITY_TESTS.md](SECURITY_TESTS.md), [KEY_METRICS.md](KEY_METRICS.md), [EVAL_DATASET.md](EVAL_DATASET.md), [COST_ANALYSIS.md](COST_ANALYSIS.md).
- **Runnable API collection**: [api/](api/) — ten requests covering the whole workflow, against the live service or a local one. Import, set two variables, run.

Who can use it: providers in the **Physicians** group (`doctor1`, `doctor2`). `admin` is denied by design, and is offered a separate **CopilotHealth** tab instead — an operational view of the agent's own counters, with no clinical content. The rounding list is *today's appointments booked for that provider, limited to their assigned patients*; book them with `scripts/seed_appointments.py`.

## Prerequisites

| Tool | Why |
|---|---|
| Windows 11 + [Docker Desktop](https://www.docker.com/products/docker-desktop/) | Runs the whole stack. PHP, Composer and Node aren't needed on the host; everything runs inside containers. |
| Git | Clone with LF line endings (see below). |
| Python 3.13 | Only for the `usecases/` test suite. |

The host doesn't need a PHP install, and the host's Node 22 is below OpenEMR's `>=24` requirement, so run every PHP, Composer, npm and PHPUnit command inside the `openemr` container.

## First-time setup

### 1. Clone with LF line endings

Files are mounted into Linux containers. Windows line endings (CRLF) break shell scripts (`/bin/sh^M`) and make every file show as modified.

```powershell
git clone -c core.autocrlf=input -c core.eol=lf https://labs.gauntletai.com/debudash/openemragent.git D:\Dev\OpenEMRAgent
```

### 2. Start the stack

```powershell
cd D:\Dev\OpenEMRAgent\docker\development-easy
docker compose up --detach --wait
```

The first run takes **10–20 minutes**: Composer install, theme build and database install. To follow along:

```powershell
docker compose logs -f openemr    # ready when you see "Starting apache!"
```

Composer downloads from GitHub without a token, so it can hit `HTTP/2 504` errors or rate limits. The container then restarts and retries, usually successfully from cache. Because of that, `up --wait` can exit 1 even though the stack recovers, so check `docker compose ps` before treating it as failed. If it keeps failing, set your own `GITHUB_COMPOSER_TOKEN` in `docker-compose.override.yml`.

### 3. Check that it installed

Sign in at http://localhost:8300/ as **`admin` / `pass`**.

Don't rely on `/meta/health/readyz`. It reports `setup_required` even on a working install, because a global variable gets overwritten when it loads. A reliable check is `sites/default/sqlconf.php` containing `$config = 1;`.

### 4. Local overrides

Machine-specific settings go in `docker/development-easy/docker-compose.override.yml`. Git ignores it, and Compose merges it in automatically. Here it sets `XDEBUG_PROFILER_ON: 0`, which turns off the profiler that otherwise writes a file on every request.

## Daily use

| Task | Command (from `docker/development-easy`) |
|---|---|
| Resume the stack | `docker compose up --detach --no-recreate --wait` |
| Pause / resume | `docker compose stop` / `docker compose start` |
| Status | `docker compose ps` |
| Shell in the app container | `docker compose exec openemr sh` |
| Run OpenEMR dev tools | `docker compose exec openemr /root/devtools <command>` |

**Avoid recreating containers you don't need to.** A plain `docker compose up` recreates any container whose settings no longer match the compose files. The data survives in named volumes, but the container re-runs its startup. So:

- Use `--no-recreate` (or `start`) for everyday resumes.
- After a deliberate change to a compose file, run `docker compose up --detach --dry-run` first and check that any `Recreate` it lists is the one you expect.
- Don't use `down`, `--force-recreate` or `--build` unless you mean to.

## Sample data

### What's loaded

**50 synthetic patients** generated by Synthea and imported through OpenEMR's own CCDA importer. Each patient has a full synthetic medical history, from birth to the day of import.

| Data | Rows | Coverage |
|---|---:|---|
| Patients | 50 | 26 female, 24 male; ages 0–100 (mean 36); all have a UUID |
| Encounters | 2,128 | Dates from 1930-03-04 to 2026-09-14 (lifetime histories) |
| Problems (`lists.medical_problem`) | 1,750 | All 50 patients |
| Prescriptions | 306 | 47 of 50 patients (a matching 306 in `lists.medication`) |
| Allergies | 59 | Many patients have none |
| Immunizations | 768 | |
| Procedure orders / results | 7,391 / 16,783 | Includes lab results |
| Vitals forms | 50 | **One per patient**, so there's no vitals trend over time |
| Care plans | 0 | Not imported |
| Facilities / users | 1 / 5 | Default install |

These counts come from the database on 2026-09-15.

**What it looks like clinically:** Synthea records social and screening findings as problems, so the most common "problems" are *Medication review due* (401), *Stress* (146), *Full-time employment* (121) and *Gingivitis* (118). Chronic conditions and medications are there too, such as simvastatin, metoprolol and clopidogrel. The most common prescription is sodium fluoride gel (38). An agent that summarizes a patient's problem list should separate social findings from actual disorders.

### How it was loaded

The data was loaded with OpenEMR's built-in devtools command:

```powershell
cd D:\Dev\OpenEMRAgent\docker\development-easy
docker compose exec -T openemr /root/devtools import-random-patients 50
```

(From Git Bash, prefix it with `MSYS_NO_PATHCONV=1`.) This runs `importRandomPatients` in `docker/binary/utilities/devtoolsLibrary.source`, which:

1. Installs Java 17 in the container and downloads `synthea-with-dependencies.jar` to `/root/synthea`. This happens only on the first run.
2. Generates *N* living patients as C-CDA documents in `/tmp/synthea/output/ccda` (FHIR export is turned off).
3. Temporarily enables `contrib/util/ccda_import/import_ccda.php` and runs it as the web server user in development mode. That mode skips document storage and the audit tables and writes patient data straight in, then assigns UUIDs.

Each patient takes several seconds. **The patients are random**, so every run produces a different dataset. Use the snapshot below to get the same data again.

### Snapshot and restore

A database dump was taken right after the import:

```
D:\Dev\openemr-snapshots\openemr-synthea50-20260914-194243.sql.gz   (6.2 MB)
```

It's stored **outside the repo** and isn't in git, so copy it yourself if you need it on another machine. It was made with:

```bash
# Git Bash, from docker/development-easy
MSYS_NO_PATHCONV=1 docker compose exec -T mysql \
  mariadb-dump -uroot -proot --single-transaction --routines --triggers --databases openemr \
  | gzip > /d/Dev/openemr-snapshots/openemr-synthea50-$(date +%Y%m%d-%H%M%S).sql.gz
```

To restore it (not yet tested; the dump uses `--databases`, so it recreates and selects the `openemr` database itself):

```bash
gzip -dc /d/Dev/openemr-snapshots/openemr-synthea50-20260914-194243.sql.gz \
  | MSYS_NO_PATHCONV=1 docker compose exec -T mysql mariadb -uroot -proot
```

## Checking the stack: `usecases/` tests

[usecases/](usecases/) is a pytest suite that asks the questions a clinician or clinical agent would ask. It uses the same route an agent would: OAuth2 password grant → FHIR R4 / REST → service layer → MariaDB. See [usecases/USECASES.md](usecases/USECASES.md) for the full table.

| ID | Checks |
|---|---|
| UC0 | Sample data is loaded (≥ 50 patients, UUIDs, encounters, problems, medications, vitals) |
| UC1–UC8 | Find a patient by name; problems, medications, allergies, vitals, visits and immunizations; REST and FHIR agree |
| UC9–UC10 | No token → 401; a token scoped to `Patient.read` can't read Conditions |
| UC11 | Clinician web login reaches the main app |

```powershell
cd D:\Dev\OpenEMRAgent\usecases
python -m venv .venv
.venv\Scripts\pip install -r requirements.txt
.venv\Scripts\python -m pytest
```

It needs the stack running. By default it targets `https://localhost:9300` as `admin` / `pass`; override with `OPENEMR_BASE_URL`, `OE_USER` and `OE_PASS`. The suite registers a temporary OAuth client, enables it directly in the database, and deletes it at the end.

It also runs against the Railway deployment: set `OE_DB_VIA=railway` and `OE_DB_PASS` so its database queries go through `railway ssh` instead of the local docker stack (see [usecases/USECASES.md](usecases/USECASES.md)).

**Last runs: 18/18 local and 18/18 against Railway (2026-09-15).**

# OpenEMR

[OpenEMR](https://open-emr.org) is a Free and Open Source electronic health records and medical practice management application. It features fully integrated electronic health records, practice management, scheduling, electronic billing, internationalization, free support, a vibrant community, and a whole lot more. It runs on Windows, Linux, Mac OS X, and many other platforms.
