Supervisor, workers and evidence

What happens between a clinician opening a chart and the answer on screen.

Where it runs

Three tiers, as in Week 1. The browser talks only to OpenEMR. The module decides who you are and which patients are yours, then calls the agent over a private network with a signed request. Only the agent talks to a model.

The patient dashboard port

Separate from the co-pilot, on branch dashboard-modernization. The legacy 2,080-line PHP dashboard, rebuilt as a React and TypeScript app that reads only FHIR.

Login

SMART on FHIR through fhirclient: authorization code with PKCE, an OpenID Connect ID token, read-only scopes for one patient. Inside the chart it reuses the OpenEMR sign-in.

Cards

Header, Allergies, Problems, Medications, Prescriptions with history, Care Team, latest Vitals. Each FHIR response is parsed into a typed model at the boundary.

Writes stay in OpenEMR

Edit opens the legacy OpenEMR editor, under OpenEMR's own ACLs. The app only reads. One global setting switches the chart between old and new.

Link to the co-pilot

LinkGate accepts a link by FHIR patient id and refuses one that does not match the open chart, before the page renders.

Gate and delivery

No model runs in the gate. Every case replays a recorded model output through the real code, so a rate limit cannot silence it.

Three things the platform taught

  • Build the refusal path like the acceptance path. A correctly refused document was reported as "was read". Pydantic dropped the unmodelled refused field, an empty PHP array encoded as [], and createDocument() takes its data by reference.
  • Test on the platform you ship to. Railway ran 8.0.0 while every test ran 8.2.0-dev. Three failures, none visible locally. Fixed by building the image from this repo.
  • A rubric that cannot fail is worse than a missing one. no_phi_in_logs passed 74/74 against an empty log. A test now asserts the gate reads a non-empty log.
