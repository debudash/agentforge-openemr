OpenEMR Architecture Map

A PHP 8.2 electronic health record that has two codebases in one: a procedural legacy app that renders pages, and a typed OpenEMR\ core that serves REST and FHIR. Both use the same service layer and the same MySQL schema.

  • 281 tables in sql/database.sql
  • 96 REST routes
  • 71 FHIR R4 routes · US Core 3.1.0
  • 132 service classes
  • 80 event classes

System context

Everything runs inside one openemr container (Apache + PHP). It has four entry points. The three auxiliary services it calls are what the dev stack starts next to it.

How an API request is handled

apis/dispatch.php wraps the request in HttpRestRequest and passes it to ApiApplication. That is a Symfony HttpKernel (OEHttpKernel) with these subscribers registered in this order. The order matters: the site and database have to exist before auth runs, and auth has to pass before a route is resolved.

Each route is a closure that does an ACL check and then calls a controller, which calls a service. For example, "GET /api/patient/:puuid" calls RestConfig::request_authorization_check($request, "patients", "demo") and then PatientRestController::getOne(), which calls PatientService::getOne(). The patients / demo pair is a gacl section and value, so every API path is still checked against the same role-based ACL that the UI uses.

Where the code lives

File counts per top-level directory, on one scale. New code is supposed to go in src/. The legacy trees are still large and still used on every page load.

Data layer

Schema, as installed

sql/database.sql creates 281 tables, and versioned sql/*_upgrade.sql files move old installs forward (starting at 2.6.0). The central tables are patient_data, form_encounter, forms, lists (problems, allergies, medications), prescriptions, billing and openemr_postcalendar_events.

Access, going forward

Services go through QueryUtils (or legacy sqlStatement()) using bound parameters. Both sit on Doctrine DBAL 4, with an ADODB-compatible interface kept for old code. New schema changes use Doctrine Migrations in db/Migrations/. Connections come only from DatabaseConnectionFactory.

Identity

Internal integer keys (pid, encounter) stay internal. APIs expose UUIDs from UuidRegistry, so most routes use :puuid and :euuid. A few older nested routes, like …/encounter/:eid/vital, still take integer IDs.

What the co-pilot adds

No tables. The agent owns no schema and writes nothing: it reads through the service layer per request, holds a chart in memory for the life of a session, and drops it. Its only schema is a typed wire contract (24 Pydantic models) validated at the boundary. Nothing persisted is nothing to retain, encrypt or breach — and it keeps the EHR the single system of record, which is what makes “every claim cites a record fetched this turn” mean anything.

Multi-site

Each directory under sites/ is its own site: sqlconf.php for database credentials, config.php, documents/ and LBF layouts. SiteSetupListener and globals.php pick one per request.

Where the agent plugged in

These were the integration options, least to most invasive. The Clinical Co-Pilot has since been built on this repo, so each is marked with what actually happened.

  • FHIR R4 over OAuth2. Narrow SMART scopes against /apis/default/fhir/*; tokens, scopes, ACLs and the API audit log all apply automatically. Not taken: eight sequential FHIR calls measured 11.4 s, against 1.0 s to read five complete charts through the service layer, and the co-pilot needed a panel inside the UI regardless.
  • Standard REST API. /apis/default/api/* covers writes FHIR here doesn’t. Taken for writes: the nightly rounding-list seeder books appointments through it, so validation and audit logging run rather than being bypassed by raw SQL.
  • Custom module — taken. oe-module-copilot-agent appends its tab through a MenuEvent listener rather than editing the tracked menu JSON, so it survives every merge from upstream, and reads charts through the service layer.
  • Direct SQL (avoid). Used once, narrowly: PrescriptionService drops end_date, and medication status is derived from that date rather than from the active flag, which a stopped drug can still carry.

The warning in the third option turned out to be literal. OpenEMR’s ACLs are role-based and never restrict a clinician to their own patients — measured, not assumed — so that boundary does not exist until you build it. The co-pilot enforces it at four independent layers, and the browser never reaches the agent or the model: every request is proxied through this module under the clinician’s own session.
