Dashboard Port Review Q&A

Short answers for the review. The defense (PATIENT_DASHBOARD_MIGRATION.md) sets the agenda; this sheet covers what someone might dig into. Amber cards are the deviations and limits: state them plainly.

The one story

A doctor opens a patient in OpenEMR and gets the new dashboard in the chart, in one click. It reads everything through the FHIR API and edits through OpenEMR's own editors. The standalone URL exists only to demo the login.

The tool ADR 0001

Why React, and not Vue, Svelte or Angular?

React escapes every value by default, and the old page's worst bugs were unescaped values. It also has the largest SMART on FHIR ecosystem, including the reference client we use.

If pushed: Vue and Svelte would work, but offer nothing to offset the smaller ecosystem. Modern Angular shares little with OpenEMR's AngularJS 1.8 and is heavy for six cards.

docs/adr/0001 · dashboard-modernization/03-migration-spec.md §3

Why not keep PHP and add htmx or Alpine?

That isn't a framework port, and it keeps the server-rendered model that produced the bugs: the page decided what to draw and its endpoints trusted that decision.

dashboard-modernization/02-bug-catalog.md (the pattern behind the worst rows)

Why TypeScript? Isn't that overhead for six cards?

FHIR is optional fields everywhere. Each response is parsed into a typed model at the boundary, so a missing field fails at build or parse time instead of showing a blank to a clinician.

Why Vite and not Next.js?

Vite builds plain static files. Next.js or any server rendering adds a second backend that would hold tokens and patient data, which the brief rules out in spirit.

What did moving off PHP actually buy?

Authorization moved to where the data is (the API checks every request), escaping is on by default, and every card is testable in seconds without a database. One 2,080-line PHP file becomes a small app whose only input is API responses.

API and data ADR 0008

Does it really use only the API?

Yes. Every value comes from FHIR: Patient, AllergyIntolerance, Condition, MedicationRequest, CareTeam, Observation. The app sends GET requests only; lint bans any other network call.

Why is it served from OpenEMR and not as its own site?

OpenEMR's API can't be called from another web origin. Its CORS handler runs after authorization and routing, so the browser's preflight gets a 404. We proved it in a spike, then served the app from OpenEMR's public/ folder. No OpenEMR code changed for that.

docs/adr/0008 · catalog API-04 · 04-evidence/spike-4.0.md

Why one patient per token? Why not a user-wide token?

OpenEMR only lets browser apps (public clients) have patient-scoped tokens. That's the right shape anyway: the dashboard shows one patient, so the token can read only that patient.

catalog API-06

Why no refresh token?

A browser app has nowhere safe to keep one. A sign-in lasts one access token; in the chart, reopening the patient simply launches again.

What can't FHIR tell you that the old page showed?

Three things a user might notice. OpenEMR reports every patient as active, so status comes from the deceased fields. The "Nothing Recorded" versus "No Known Allergies" wording depends on a flag FHIR doesn't carry. Care team members have no status, so an inactive one is still listed.

Login ADR 0009

The brief requires OAuth2 / OpenID Connect. Where is it?

Every open runs a SMART on FHIR authorization-code exchange with PKCE and returns an OpenID ID token naming the doctor. In the chart it's single sign-on, so there's no screen to see. The standalone URL shows the full login, patient picker and consent, and that's what I demo.

Why doesn't the chart ask the doctor to log in again?

OpenEMR reuses the doctor's session for an in-EMR launch when the admin marks the app as trusted. It's an OpenEMR feature, not ours, and it's the admin's decision per app.

Trade-off

Isn't the "trusted app" flag risky?

It skips the login and consent screens for that one app, which gets only the read scopes it registered, for the patient on screen, as the signed-in doctor. It's meant for the clinic's own app. Untrusted, the app still works; the doctor logs in and approves each time it opens.

The OpenEMR change ADR 0009 · 0010

Deviation

The brief says don't touch the backend. Did you?

Yes, once, deliberately, and it's in the defense. One page (demographics.php) and two settings, so clicking a patient opens the new dashboard inside the EMR. Without it the doctor leaves the EMR, logs in again and picks the patient again, which no clinician would do.

If pushed: it's off by default, rollback is one setting, and with it off the page is exactly as before.

Why not use OpenEMR's existing "SMART Enabled Apps" launch card?

That works with no code change, and we proved it. But the card is collapsed at the bottom of the old dashboard, so the doctor still sees the old page first. Changing one page makes the new dashboard what "open patient" means.

04-evidence/spike-ehr/spike-ehr-launch.md

How does editing work if the app is read-only?

In the chart, Edit opens the same OpenEMR editor the old card opens: the issue editor for allergies, problems and medications, and the prescription dialog. Saving happens there, under OpenEMR's own permission checks. The app only names the action; the chart page builds the URL and accepts the request only from its own frame.

Why not edit inline in the new cards?

That would mean writing through the API, and the API's permission gap (next section) would let a restricted user change clinical data. Reusing OpenEMR's editors gives parity without a new write path.

You also changed the old dashboard's code. Why?

The audit found real security bugs in it: care team and preference writes with no permission check, patient data sent before the permission check, and stored XSS. The old page stays in the product, so we fixed them, each reproduced first by a failing test, in a separate commit.

Security API-11 · BUG-110

Known limit

Can a user see data they shouldn't?

In the chart, no. On the standalone login-demo URL, yes, for one kind of user: someone allowed to see demographics but not clinical data. OpenEMR's FHIR API doesn't apply the user's own permissions to patient-scoped tokens. The chart only opens the app for users with clinical access; the real fix is in OpenEMR's API, and a test records the gap so it can't be forgotten.

docs/adr/0010 · dashboard/e2e/known-limits.spec.ts · 04-evidence/in-chart/upstream-issue-api-acl.md

Why didn't this show up in the old dashboard?

The old page never used the API. It checked each card's permission in the same PHP code that read the data. The gap was always in the API; moving onto the API made the API the only gate and exposed it.

What about squads?

The old page meant to restrict out-of-squad patients but only hid the header; we fixed that, so the chart now refuses the whole page first. The API doesn't know about squads, but no patient on this stack uses them.

How do you stop XSS in the new app?

React renders text only. Lint bans every HTML sink, and a test puts an <img onerror> payload in every card field and checks it shows as text.

Parity

How do you prove it's the same dashboard?

A harness renders the old and new dashboards for all 50 patients on the dev stack, as the same doctor, and compares every card item by item. A difference without a documented reason fails the run. None was unexplained.

dashboard/e2e/parity.spec.ts · 04-evidence/parity/parity-report.md

What's different, then?

Only presentation details: empty-list wording, BMI shown as recorded instead of rounded, "23 months" instead of "23 month", and care team names as "Given Family". One is flagged: the inactive care team member, because FHIR doesn't carry member status.

Prescriptions: why did the counts differ at first?

The first version showed active prescriptions only. The old card is "Prescription History", which gives clinicians the context of ended ones, so we restored it: current first, then ended, with a status column. It now matches the old card exactly (140 of 140 items on the 10 patients with the most history).

04-evidence/prescription-history/README.md

Did you redesign anything?

No. Same cards, same order, same Bootstrap 4.6 styling OpenEMR ships. The additions the brief asked for are sex and status in the header, plus Vitals as the extra section.

Testing

How is it tested?

Unit tests per card over responses recorded from the dev stack, which run in seconds in CI. Playwright end-to-end tests through the real login, in the chart and standalone. The parity harness. Browser tests for every refusal path: the wrong patient, a racing patient switch, restricted users, forged edit messages.

How do you know the tests would catch a regression?

We broke each rule-carrying line on purpose, one at a time, and confirmed a named test or lint rule failed every time.

04-evidence/unit-test-mutations.txt

Why don't the browser tests run in CI?

They need a running OpenEMR stack, which the pipeline doesn't have. CI runs lint, typecheck and unit tests. The browser suites run locally, and their reports are committed as evidence.

How did you work out what to build?

Audit first: a dependency tree of the old page, a per-file audit of 51 files, a bug catalog, then a migration spec with ten design rules and a decision per open question, before any code.

dashboard-modernization/ (00-tree through 03-migration-spec)

Limits and next

Is it deployed?

Yes, on the public Railway instance. Open any patient and the chart shows the new dashboard; /public/dashboard/ is the login demo. The image build compiles the app into OpenEMR's public/dashboard/ and leaves its source out of the web root.

If pushed: rollback is one admin setting (back to the old cards), or the previous image, which is recorded.

deploy/railway/README.md "Patient dashboard" · 04-evidence/in-chart/railway-in-chart.png

What would you do next?

Fix the API permission gap upstream (the report is drafted). After that: a launch from calendar appointments, which OpenEMR supports in code but not in its UI, and the deferred Medium and Low bugs from the catalog.

Why not fix the API permission gap yourselves?

It's a change to OpenEMR's API core, which the brief rules out, and it affects every SMART app, so it belongs upstream. We scoped around it in the chart and documented it.
